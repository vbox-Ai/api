### 2.1 qysq 妻友社区 —— 请求签名 100% 还原 ✅

**来源**：`QySqInterceptor::_generateSign` @ `0x8e100c`

```python
# 常量
SECRET   = "gH3nA7fR9tV1jY6z"                                    # HMAC key（16 字符）
DEV_UA   = "DevType=Apple iPhone mobile;SysType=light;Ver=2.1.2;BuildID=Mobile Safari 18.5"
BROWSER_UA = "Mozilla/5.0 (iPhone; CPU iPhone OS 18_5 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/18.5 Mobile/15E148 Safari/604.1"
TOKEN    = <6868 splash token 表 id=9, token_qysq>

# 签名
ts    = int(time.time())        # UTC 秒
nonce = str(uuid.uuid4())
path  = "/" + request_path      # 如 "/api/app/media/home"
msg   = f"{TOKEN}&{path}&{DEV_UA}&{ts}&{nonce}"
sign  = HMAC_SHA1(SECRET, msg)
x_api_key = f"timestamp={ts};sign={sign};nonce={nonce}"
```

**请求头（4 个缺一不可）**：
```
X-User-Agent : <DEV_UA>
user-agent   : <BROWSER_UA>
authorization: Bearer <token_qysq>
x-api-key    : <timestamp=…;sign=…;nonce=…>
```

**实测**：
- `POST /api/app/media/home` → 200 `{"code":6023,"data":"<base64密文>","hash":true}`
- `POST /api/app/media/short/hot` → 200 `{"code":200,"data":"<base64密文>"}`
- `GET /api/app/ping/config` → 200 code=200（签名通过）

**剩余卡点**：响应 `data` 是 base64 密文（`%16 = 12` → **密文从 D[12] 开始**，此点已钉死）。
已试：9 种偏移 × 6 组 key（secret/md5/sha1 派生）× 5 组 IV = 0 命中。

**2026-11-03 15:20 更新（仍是卡点，但范围收窄）**：
- 解密函数已定位 = `CryptoUtil::asGjCrypto` @0x7237f0（`QySqHttp.post` 调完直接 jsonDecode）
- 32B 盐 `vEukA&w15z4VAD3kAY#fkL#rBnU!WDhN`（libapp.so @521089）；两段 sha256 KDF；
  `Key(x)+AES(AESMode)+Encrypted(D[12:])+IV(y)` 的结构已确认
- 又扫约 **120 万组合**（sha256/384/512 × 顺序 × 切片 × CBC/CFB/OFB × skip∈{0,12,16,24}）全 0 命中
- 结论：blutter 里 `[fp-8]/[fp-0x18]` 槽位的写回顺序读错 → 需**逐指令重放**或**真机 Frida** hook 该函数

## 六、mdtv 深度修正（第二轮，2026-11-03 晚）

### 6.1 之前两处关键错误（已修正）

| 项 | 错误值 | 正确值 |
|---|---|---|
| 请求加密 key | `-p9B[~PnPsJGDZMX`（16B，当 AES-128 用） | **`Vq234zBeSdGgYXzVTEfnnjjdmaTkk7A4`（32B，AES-256）** |
| 签名 secret | 借用 aijav 的 `&NRkw0g3iJLDvw5tJ5PuVt5276z0SOuyL` | **`&m}q%ea6:LDcmS\?aK)CeF287bPvd99@E,9Up^`（mdtv 专有）** |

IV 仍为 `-p9B[~PnPsJGDZMX`（16B）。

### 6.2 精确的请求加密流程（`MdTvInterceptor::onRequest`）

```
1) biz = {业务参数}
2) biz["timestamp"] = 秒级时间戳                      ← 关键：timestamp 在签名前就放进 map
3) joined = "&".join(f"{k}={biz[k]}" for k in sorted(biz.keys()))
4) biz["encode_sign"] = MD5(joined + "&m}q%ea6:LDcmS\?aK)CeF287bPvd99@E,9Up^")
5) post_data = base64( AES-256-CBC(jsonEncode(biz), key=Vq234z…, iv=-p9B[~PnPsJGDZMX) )
6) map.clear() → map["post-data"] = post_data
7) 请求体 = {"post-data": post_data}
```

**注意**：签名串里含 `timestamp`（`0x8d5c88` 先写 map 再排序），这是第一轮漏掉的关键点。

## 七、mdtv 结案：不用抓包，两处报文细节（2026-11-03 14:35）

**没有真机抓包也破了**。回到 asm 把 `onRequest` 的**每一行赋值**重新抄一遍，
发现上一轮抄丢了两个东西，都在"加密之后/之前"的胶水层：

### 7.1 真凶一：`headers["suffix"] = "JGDZMX"`（0x8d5e64~0x8d5e84）

```
0x8d5e6c: r2 = "suffix"
0x8d5e74: r3 = "JGDZMX"
0x8d5e7c: GDT[cid_x0 + -0x122]()      ← headers.putIfAbsent/[]= 动态派发
```
服务端拿这个头拼**请求 IV**：`"-p9B[~PnPs" + "JGDZMX"` = 客户端写死的 16B 请求 IV。
头不发 → 服务端还原不出 IV → 请求体解不开 → 业务层空参 → `{"code":1002,"msg":"参数错误"}`。
**响应照样解得开**（响应 IV 只依赖响应体 `suffix` 字段），所以现象极像"参数名不对"。

### 7.2 真凶二：SECRET 没有反斜杠（`libapp.so` @367007）

blutter 把字符串里的 `?` 打印成了 `\?`，上一轮照抄成
`&m}q%ea6:LDcmS\?aK)...`，实际二进制原始字节是
`&m}q%ea6:LDcmS?aK)CeF287bPvd99@E,9Up^`（36 字符）。
补上 suffix 头后错误码立刻从 1002 变 **1001 签名错误**，把 secret 的反斜杠去掉 → `code: 0`。

### 7.3 错误码迁移就是进度条

| 步骤 | 变化 | 判读 |
|---|---|---|
| 基线（无 suffix 头 + 带反斜杠 secret） | `1002 参数错误` | 请求体没解不开，签名根本没参与 |
| 只加 `suffix` 头 | `1001 签名错误` | 请求体解开了，**证明头和密钥这条链对了** |
| 再去掉 secret 反斜杠 | `0 操作成功` | 全线通 |

### 7.4 结果

