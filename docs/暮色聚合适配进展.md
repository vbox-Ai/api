| `_adapter_for(key)` | 按 key 动态创建 Adapter |

## 九、hdb（黄豆瓣）协议详解（最复杂，作为范式参考）

### 加密流程

```
请求：
  AES key = random 16 bytes, iv = random 16 bytes
  encrypt_key = base64( RSA_encrypt(服务端公钥, {"key": b64(key), "iv": b64(iv)}) )
  encrypt_data = base64( AES-128-CBC(PKCS7(业务JSON), key, iv) )
  POST body = {"encrypt_data": ..., "encrypt_key": ...}

响应：
  encrypt_key = RSA 加密的 {"key": b64, "iv": b64}
  encrypt_data = AES-128-CBC 加密的响应 JSON
  客户端用 RSA 私钥解 encrypt_key → 拿 key/iv → 解 encrypt_data
```

### 关键要点

| 点 | 说明 |
|---|---|
| RSA 密钥 | 服务端公钥加密请求，客户端私钥解密响应（密钥对已内置） |
| AES 位数 | **128 位**（16 字节），不是 256 |
| `film_id` | 必须传**字符串**（int 会返回 200 但空 body） |
| `ltype` | 必须匹配列表项的 `belong` 字段（dailyList 项 belong=1） |
| 响应 `data` | 是**直接数组**，播放直链在 `data[0].url` |
| 限流 | 服务端有请求限流，超时设 25s + 域名轮换才稳定 |

### 接口

- `pwa/v2_0/dailyList` — 列表（参数：page, length, country:-2, censorship_type:0, date）
- `pwa/v2_0/filmDetails` — 详情（参数：film_id:str, ltype, userToken）
- `pwa/v2_0/searchV21List` — 搜索（参数：type:4, word, classification_id）

## 九之二、hgsp（黄瓜视频）协议详解 —— 666 破局过程与结论

> 2026-11-02 攻坚。签名链已 100% 还原（与文档第二节"半成功"结论不同，签名公式本身是错的）。

### 真实 host（重要）

`https://api55.nmrgqb.com/` —— 来自真机 plist `flutter.hgsp`。

**不是** `hgapi-pnt017.soymfb.com`（密钥池里的旧域名，仍在线但只是壳，任何请求都 666）。
读取方法：`muse_data.zip → Library/Preferences/com.look.avbox.plist`。

`HgSpHttp` 的 baseUrl = `SpUtil.getString("hgsp")`，即 splash 动态下发，不写在代码里。

### 正确的签名链（从 interceptor 反汇编完整还原）

```
flowId = "//" + <uuid4> + "/?Authorization="
         + "&Seq=5299c575a58ddc161fdf2CZOmDp0tCJSpEJGrC30nE0"
         + "&X-Auth-Key=368480924a6c78e2e8681551a7cf4c21"
         + "&X-Auth-Nonce=<8位数字 10000000~99999999>"
         + "&X-Auth-TimeStamp=<13位毫秒>&"

X-Auth-Sign = urlencode( base64( HMAC_SHA1(secret, base64url_utf8(flowId)) ) )
secret      = cuke@appSecret#Ten2020!0120
```

内部中间产物（不对外发送）：

```
seqMod = "07cd848d8dce6219...61988fd31"（128 字符 hex，固定）
前 16 字节 key = base64url(flowId)[:16]
AES-128-CBC(key, iv="16-Bytes--String", data=b64url(flowId))  →  base64
```

注意：`release` 不是签名参数，是 **query 参数**（`?release=506`）；签名里的"版本位"是 `terminal`。

### 网关行为（实测矩阵，关键结论）

`api55.nmrgqb.com` = openresty + Spring Boot 单体。判定分层：

| 条件 | 返回 |
|---|---|
| 无 `pkg` 头 | **666**（空体） |
| 有 `pkg`，路径不存在 | `404` JSON（Spring 标准错误体） |
| 有 `pkg`，路径存在 | `500` JSON（`No message available`）或业务错误 |
| 头数量超过约 6 个 | **再次 666**（白名单式：头太多直接拒） |

**结论：666 的触发源是 `pkg` 头，不是签名。** 只带 `pkg: cuke0001` 就能穿过 666 层。

在此之上，`/home/defaultchannels`、`/home/movlist`、`/home/actor/list`、`/home/newmov/query`
全部确认为**真实路由**（只在带 `pkg` 时从 404 变 500）。

### 当前卡点（精确到报错）

最小可通行头集合 = `pkg` + `X-Auth-Sign` + `X-Auth-TimeStamp` + `X-Auth-Nonce` + `X-Auth-Key` + `Seq`
→ 业务层返回：

```
500 {"message":"For input string: \"nul\"","path":"/home/defaultchannels"}
```

`"nul"` 是 Java `StringUtils.substring(null,0,3)` 的产物，说明**某个请求头的值为 null 却被 `Integer.parseInt` 解析**。
已排除：`Seq` 内容（换成纯数字/各片段变体，报错不变）、`uuid`、`Ip`、`terminal`、`channel`、`version`。
补到第 7 个头（任意一个，含 `release`）→ 网关立刻回退 666。

**因此存在一个窄窗口**：头上限恰好卡在"够放行、不够解析"之间。
下一步要从 XPosed/Frida 真机动态 hook `HgSpInterceptor.onRequest` 拿到**实际发送的头集合与真实 flowId 样本**，
或用 `muse_live_box` 那台的手机网络再抓一次明文（FLEX 在这台上抓的是 TLS 密文，无效）。
