# 新增远程源注意事项（v2 · 对齐 2026-11 版 vbox）

> 适用：向 `vbox-Ai/api` 新增/修改福利平台与 Python 蜘蛛
> 依据：`hf805864818/vbox-ios`（Flutter + Swift 双端，2026-11-05 提交）源码实测
> 相对 v1.1 的变化：**分类体系改为"顶层平台分类 + 平台内二级分类"**，`base/spider.py` 已自带 `fetch()`，
> 平台注册字段以真实 JSON 为准（v1.1 的 `platformId/displayName/scriptPath` 示例是错的）。

## 〇、先记住三件事

1. **App 只读 `sources/all_sources.json`**。`welfare_platforms.json` 是源文件，`all_sources.json` 里的
   `welfarePlatforms` 是派生副本（由 `domain-monitor/merge_sources.py` 生成，生成时**去掉 `_meta`**）。
   只改源文件不重新合并 → App 里根本看不到平台。
2. **分类是两层**：顶层 `categories`（video/live/comic）决定平台出现在哪个 Tab；
   平台内部的 `class` 是分类 Tab，`filters` 是每个 Tab 下的"全部 + 二级分类"胶囊。
3. **`homeContent` 必须又快又能出分类**。App 把"分类为空"当作加载失败态（显示重试），
   所以不要把网络请求放在这条路径上；失败也不要把兜底分类写进缓存。

## 一、当前 App 的分类体系（源码依据）

### 1.1 顶层：平台分类

- 数据来自 `welfare_platforms.json` 的 `categories`（当前：`video` / `live` / `comic`）。
- 平台按 `platform.category` 归组；顺序按 `sortOrder`，用户拖动排序持久化在
  `fuli_remote_platform_order_v2`，结构 `{categoryKey: [platformKey, ...]}`。
- 👉 **`platformKey` 是排序持久化的主键，一旦上线不能改**，改名/改序不影响它。

### 1.2 平台内：二级分类

`WelfareSpiderMainPage`（`lib/presentation/pages/welfare/welfare_spider_main_page.dart`）的渲染顺序：

```
homeContent() 返回的 class 列表  →  顶部横向分类 Tab（FuliCategoryTabBar）
每个 Tab 内部：
    ├─ 子分类胶囊栏：「全部」+ 二级分类（来自 filters[typeId]）
    └─ 2 列视频网格 + 加载更多 + 下拉刷新
分类导航视图（FuliCategoryNavigatorView）：4 列网格，分类 > 30 显示搜索框，支持展开二级分类
```

模型层（`lib/domain/entities/welfare/fuli_models.dart`）：

```dart
class FuliCategory {
  final String typeId;
  final String typeName;
  final List<FuliCategory>? subCategories;   // 二级分类
}
```

因此蜘蛛要给出两层：

```python
# 一级：分类 Tab
"class": [
    {"type_id": "20", "type_name": "有码影片"},
    {"type_id": "21", "type_name": "无码影片"},
]

# 二级：该 Tab 下的胶囊（key 会被放进 extend）
"filters": {
    "20": [{"key": "cate", "name": "分类", "value": [
        {"v": "20", "n": "全部"}, {"v": "26", "n": "国产精品"},
    ]}],
}
```

> 只返回 `class`、不返回 `filters` 也能用（没有二级胶囊）；返回了 `filters`，用户选中的值会以
> `extend={"cate": "26"}` 传给 `categoryContent`。

### 1.3 方法签名（与旧文档不同）

```python
def homeContent(self, filter)                       # {'class': [...], 'filters': {...}, 'list': [...]}
def categoryContent(self, cid, page, filter, ext)   # ← 形参名是 cid/ext
def detailContent(self, did)                        # ← did 是 list，取 did[0]
def searchContent(self, key, quick)
def searchContentPage(self, key, quick, page)
def playerContent(self, flag, pid, vipFlags)
```

## 二、`base.spider.py` v3 已提供什么（旧文档的最大过期点）

`vbox/Resources/python-stdlib/base/spider.py` 现在自带：

| 能力 | 说明 |
| --- | --- |
| `fetch(url, headers=None, **kw)` | 返回 `Response`（`.text/.content/.json()/.status_code`），**4xx/5xx 不抛异常** |
| `post(...)` | 同上 |
| `_apply_injected_hosts()` | 每次请求前把 `_vbox_effective_hosts[0]` 写成 `self.host`，其余进 `_backup_hosts` |
| `_vbox_proxy_enabled` / `_vbox_proxy_url` | 平台级代理注入，`fetch` 会自动改写 URL |
| `getCache/setCache/delCache` | 进程内缓存（App 常驻单例，**跨调用保留**） |
| `cleanText/removeHtmlTags/regStr/getCookie/getProxyUrl/localProxy` | 工具方法 |

所以：

- **不必再自己实现 `fetch()`**（v1.1 的第一条根因已过期）；但如果你覆盖它，返回值要兼容
  `.text/.status_code/.json()`，否则宿主或第三方代码会崩。
- 脚本里**优先用 `self.fetch()`**，这样能自动吃到域名注入与代理；直接 `urllib` 会绕过这两层。
- `getDependence()` 只声明真正 import 的三方库；基类已用 urllib 兜底，纯 urllib 脚本返回 `[]` 即可。

## 四、新增一个源的完整步骤

1. **写脚本**：`sources/welfare-js/xxx.py`，继承 `base.spider.Spider`，实现
   `getName/getDependence/init/homeContent/categoryContent/detailContent/playerContent`。
2. **本地自测**（必须有）：分类数、列表条数、详情、`playerContent` 直链可拉流、失败自愈。
3. **注册条目**：在 `sources/welfare_platforms.json` 的 `platforms` 里追加一条（字段见第三节）。
4. **重新合并**：`python3 domain-monitor/merge_sources.py`
   → 重写 `all_sources.json`（去 `_meta`）+ bump `manifest.configVersion` + 写 `manifest.version`。
5. **一次提交**：脚本 + `welfare_platforms.json` + `all_sources.json` + `manifest.json` + `manifest.version`。
   分多次 push 会让 `bump-version` 工作流并发冲突（红 X）。
6. **核对**：`all_sources.json` 与 `welfare_platforms.json` 的 `platforms` 数量一致、`platformKey` 不重复。

## 五、性能与超时（App 侧硬约束）

- Python 引擎单次调用上限约 **20s**；`categoryContent` 里做多域名探测要留余量。
  推荐：探测预算 ≤ 12s + 单请求超时 ≤ 7s。
- `homeContent` 应**零网络**或极轻（返回缓存/内置分类），否则首屏会卡在加载态。
- 列表页请求失败**不要写缓存**；只缓存成功结果，并在 `init()` 里重置进程内状态。

## 六、失败缓存毒化（v1.1 的坑，仍然成立）

App 的 Python 引擎是**常驻单例**，一次 `homeContent` 也被当作域名可用性探针。
若失败时把兜底分类写进 `getCache`，会**整个会话都只剩那一个分类**。

```python
def init(self, extend=""):
    self._class_cache = None          # ① 每次初始化重置
    ...

def _classes(self):
    if self._class_cache:
        return self._class_cache
    classes = []
    for _ in range(2):                # ② 轻量重试
        items = self._fetch_classes()
        if items:
            classes = items
            break
    if classes:                       # ③ 只有成功才缓存
        self._class_cache = classes
    return classes
```

## 七、播放返回格式

```python
# 直链（推荐）
return {"parse": "0", "url": "https://.../index.m3u8", "header": {"Referer": ..., "User-Agent": ...}}

# 需要解析器
return {"parse": "1", "playUrl": "", "url": "https://.../play/123"}
```

- `parse` 用字符串 `"0"/"1"`（与现有脚本一致）。
- 漫画：`{"parse": "0", "url": "manga://img1&&img2"}`；图集：`pics://`；小说：`novel://{json}`。
- 直链有时效签名，`playerContent` 每次现取，不要缓存直链。

## 九、常见坑（更新版）

| 坑 | 说明 | 解决 |
| --- | --- | --- |
| 只改 `welfare_platforms.json` | App 读 `all_sources.json`，平台不显示 | 跑 `merge_sources.py`，两文件一起提交 |
| 分类为空 | App 判为加载失败，显示重试 | `homeContent` 返回内置/缓存分类，别依赖网络 |
| 失败也缓存 | 整个会话只剩兜底分类 | 只在成功时 `setCache`，`init` 重置 |
| 绕过 `self.fetch` | 丢失域名注入与代理 | 统一用 `self.fetch`，或自行实现 `_vbox_effective_hosts` |
| `parse` 用 int | 个别路径判空 | 用字符串 `"0"/"1"` |
| 分页从 0/1 开始不一致 | 少一页/重复首页 | 按站点确认后 ±1 |
| 编码乱码 | 中文站常见 | `r.encoding='utf-8'` 或按 header 探测 |
| 版本冲突 | 多个 commit 触发多次 bump | 一次改动一个 commit，推送前 `pull --rebase` |

## 十一、性能模式（照搬即可）

> 来源：X99 导航源实机调优。任何"站点多、页面大、跨境慢"的源都可以直接套。

### 11.1 首屏分类不要发网络请求

```python
def homeContent(self, filter):
    classes = self._snapshot_classes()      # 内存里的快照，2-3ms
    self.kick_refresh()                     # daemon 线程后台抓真实分类，24h 缓存
    return {"class": classes, "filters": {}, "list": []}
```

App 把 `homeContent` 当首屏探针，一旦这里慢，整页卡在加载态。

### 11.2 连接复用（省 300–400ms/次）

```python
_POOL = threading.local()
conn = _POOL.map.get(host) or http.client.HTTPSConnection(host, context=_SSL)
conn.request("GET", path, headers={..., "Connection": "keep-alive", "Accept-Encoding": "gzip"})
resp = conn.getresponse()
if resp.will_close: _drop(host)             # 服务端要关就丢弃
```

配套：断连重试一次、3 跳内跟随 302、gzip 解压（58KB → 16KB 的站很常见）。

### 11.3 列表缓存：单键 + TTL + 上限

```python
LIST_TTL, LIST_MAX = 180, 40
store = {k: v for k, v in self._lists().items() if now - v["ts"] < LIST_TTL}  # 先清过期
store[key] = {"data": data, "ts": now}
if len(store) > LIST_MAX:                    # 再裁剪
    store = dict(sorted(store.items(), key=lambda kv: kv[1]["ts"], reverse=True)[:LIST_MAX])
```

避免"每键一条、只过期不删除"导致长会话内存只涨不降。

### 11.4 预测性预取

- **进入即预热**：`homeContent` 后后台抓"有分类的平台"的首个分类（每会话一次）；
- **点击后预取**：返回列表后并行抓同平台另外 3 个分类（每平台 10 分钟一次）。

实测：首次点开 0ms（命中预热），换分类 0ms（命中预取）。

### 11.5 红线

| 项 | 建议值 |
| --- | --- |
| 首屏耗时 | < 50ms |
| 单次 categoryContent | < 5s（超时上限 20s 的一半以内） |
| 预热流量 | < 400KB / 会话 |
| 列表缓存 | ≤ 40 条 / ≤ 300KB |
